# Sprint 6 Wrap-up

## 1. A design decision from Module 4/5 that survived (or changed) in Module 11

The REST resource shape decided in Module 4 — `POST /accounts/{accountId}/orders` as a sub-resource of the account, rather than a flat `POST /orders` — survived completely unchanged into Module 11's assembled service. It was expressed first in the critique (`redesign-template.md`), then in the OpenAPI spec (`order-service.yaml`), and Module 11's `@RequestMapping("/accounts/{accountId}/orders")` in `OrderController.java` is identical in structure. Neither the persistence layer (Module 7's MyBatis AccountMapper) nor the JWT security (Module 9's SecurityConfig) forced a change: both adapted to the URL shape rather than the other way around. The only design decision that *did* require revisiting was the response body — `OrderResponseDto` in Module 6 returned `{id, status, fee, reason}` matching a standalone order, but Module 11 added `newHoldingQuantity` once the holding update was wired in, because a client actually needs to know their new position after a trade settles.

## 2. Sprint 5's business logic did not need rewriting

The mission brief's claim was accurate. `domain/OrderValidator.java`, `domain/HoldingUpdater.java`, `domain/InstrumentFactory.java`, and the three `Instrument` subclasses (`EquityInstrument`, `BondInstrument`, `FundInstrument`) were copied verbatim from Sprint 5's Module 13 into Module 11's `domain/` package and were never edited. The comment on line 4 of `OrderValidator.java` makes this explicit: "Carried over from Sprint 5, Module 13 UNCHANGED." The only things that changed around them were the input sources (an `OrderRequestDto` via HTTP instead of a parsed CSV line) and the output targets (a JSON response and a Postgres write instead of a console print) — which is exactly the point of separating domain logic from infrastructure.

## 3. The deliberate simplification in Module 11

Module 11 computes `currentPortfolioValue` as `currentHoldingQuantity * dto.price()` — using the *incoming order's own price* as a proxy for the current market price of the holding, rather than fetching a real market price. This is a reasonable training trade-off because the Sprint 3 enterprise schema has no live price feed table, and building one would have taken a full sprint by itself. Using the order price keeps `OrderValidator`'s real business rule exercised against real data (a buy that exceeds the £2 million risk limit is still caught) without fabricating infrastructure the sprint was not designed to build. In production this shortcut would be unacceptable — the risk limit calculation would need current market prices, not the price the client is offering to pay today, which is a different number and not a reliable basis for a risk check.

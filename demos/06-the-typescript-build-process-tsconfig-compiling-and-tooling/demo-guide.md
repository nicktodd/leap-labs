# Module 6 Demo Guide — The TypeScript Build Process: tsconfig, Compiling & Tooling

Module 5 compiled a single file by hand: `npx tsc file.ts --strict`. That doesn't scale
past one file, and it's not how any real TypeScript project is actually built. This
module replaces the ad hoc flags with a real project: a `tsconfig.json`, a `src/` folder,
a `dist/` output folder, and the npm scripts that tie them together.

**Compare to Java, up front:** this is TypeScript's version of a Maven or Gradle build
file — `tsconfig.json` is where compiler behaviour is configured once, instead of typed
as flags on every command, the same way `pom.xml` configures `javac`'s behaviour instead
of every developer remembering the right command-line flags.

## Part 1: The Project Layout

```
06-.../
  src/
    attempt.ts      <- Module 5's Attempt interface and functions, moved here
    index.ts         <- imports from attempt.ts, the "entry point"
  dist/               <- generated by tsc - never edited by hand, never committed
  tsconfig.json
  package.json
```

`attempt.ts` is Module 5's `Attempt` interface and functions, moved into their own file —
a real project splits typed code across files exactly like Module 3 split plain
JavaScript across `.mjs` files.

## Part 2: tsconfig.json, Option by Option

```json
{
  "compilerOptions": {
    "target": "ES2022",
    "module": "NodeNext",
    "moduleResolution": "NodeNext",
    "rootDir": "src",
    "outDir": "dist",
    "strict": true,
    "declaration": true,
    "sourceMap": true
  },
  "include": ["src/**/*"]
}
```

- **`target`** — which JavaScript version the OUTPUT should target. `ES2022` means the
  compiled `.js` can use modern syntax (like `??`, top-level `await`) without being
  rewritten into older equivalents.
- **`module`** / **`moduleResolution`** — `NodeNext` tells `tsc` to compile
  `import`/`export` the way Node's own ES modules expect (Module 3's `.mjs` behaviour),
  and to resolve `import` paths the same way Node does.
- **`rootDir`** / **`outDir`** — where source lives, where compiled output goes. `tsc`
  refuses to compile a file outside `rootDir`, and mirrors `src/`'s folder structure
  inside `dist/`.
- **`strict`** — turns on the whole family of strict checks at once (including Module
  5's `noImplicitAny`), rather than naming each one individually.
- **`declaration`** — generates a matching `.d.ts` file for every `.ts` file, letting
  OTHER projects import this code with full type information, without needing the
  original `.ts` source.
- **`sourceMap`** — generates a `.js.map` file next to each `.js` file, so a debugger (or
  a stack trace) can point back at the ORIGINAL `.ts` line, not the compiled `.js` line.

**Compare to Python:** there's no strict equivalent to most of this in plain Python —
`mypy` has its own separate `mypy.ini`/`pyproject.toml` config, entirely optional, and
Python never produces a separate "compiled output" folder the way `tsc` does.

## Part 3: Building the Project

```bash
npm run build
```

This runs `tsc` (configured in `package.json`'s `scripts.build`) with no file argument —
in project mode, `tsc` reads `tsconfig.json`, compiles everything under `include`, and
writes it all to `dist/`.

Verified real `dist/` contents after building:

```
dist/attempt.d.ts
dist/attempt.js
dist/attempt.js.map
dist/index.d.ts
dist/index.js
dist/index.js.map
```

Open `dist/attempt.d.ts` — this is what `"declaration": true` produced:

```typescript
export interface Attempt {
    username: string;
    outcome: string;
}
export declare function describeOutcome(outcome: string): string;
export declare function describeAttempt(attempt: Attempt): string;
```

All the type information, none of the implementation — exactly what another TypeScript
project would need to import this code with full type checking, without ever seeing how
`describeAttempt` is actually implemented.

Run the built output:

```bash
npm run start
```

Verified real output:

```
alice logged in successfully
```

## Part 4: A Real tsconfig Gotcha

`src/index.ts` imports `attempt.ts` like this:

```typescript
import { describeAttempt, type Attempt } from "./attempt.js";
```

That's not a typo — `NodeNext` module resolution requires the `.js` extension in the
import, even though the actual file on disk is `attempt.ts`. The import path describes
where the COMPILED file will be, not the source file. Remove the `.js` and rerun
`npx tsc --noEmit`:

Verified real compiler output:

```
src/index.ts(1,47): error TS2835: Relative import paths need explicit file extensions
in ECMAScript imports when '--moduleResolution' is 'node16' or 'nodenext'. Did you mean
'./attempt.js'?
```

This trips up nearly everyone the first time — it's worth hitting live rather than just
described, precisely because the fix (`tsc`'s own suggestion) is the same "did you mean"
pattern Module 5 already saw for a typo'd property name.

## Part 5: Tooling — Running TypeScript Without a Separate Build Step

The build/run cycle above (`npm run build`, then `npm run start`) is the right shape for
shipping code, but slow for active development — recompiling by hand after every change
gets old fast.

```bash
npm run dev
```

(`scripts.dev` runs `tsx src/index.ts`)

Verified real output:

```
alice logged in successfully
```

Same result, no `dist/` folder produced at all. `tsx` compiles the `.ts` file in memory
and runs it directly, on every run — convenient for development, but it does NOT replace
`npm run build` for anything that actually ships. `tsx` is roughly TypeScript's
equivalent of running a `.py` file directly with `python` rather than compiling it first
— nothing to compile ahead of time is exactly the point.

**Compare to Java:** there's no real Java equivalent to `tsx` — Java's `javac` step and
its `java` run step are both mandatory and separate; there's no widely-used tool that
skips straight from `.java` source to a running JVM the way `tsx` skips from `.ts`
straight to a running Node process. Java 11+'s single-file source-code launcher
(`java Foo.java`) is the closest comparison, though it's used far less commonly than
`tsx`/`ts-node` are in the TypeScript world.

## A Running Comparison

| TypeScript | Java | Python |
|---|---|---|
| `tsconfig.json` | `pom.xml` / `build.gradle` | `pyproject.toml` (project metadata; `mypy.ini` for type checking, separately) |
| `npm run build` (`tsc`) | `mvn compile` / `./gradlew build` | No real equivalent — Python doesn't compile to a separate output folder |
| `dist/` | `target/` | No real equivalent |
| `.d.ts` declaration files | `.class` files carry their own type info already | `.pyi` stub files (rare, mostly for libraries) |
| `tsx` (run without building) | `java Foo.java` (single-file launcher, Java 11+, rarely used) | `python file.py` (never compiles first, by default) |

## Transition to the Lab

Learners set up a small two-file TypeScript project from scratch: write a `tsconfig.json`
matching this demo's settings, split typed code across `src/` files, build it, and fix a
deliberately broken import path (Part 4's gotcha) to get a clean build — verified by
`npm run build` producing a working `dist/` and `npm run start` printing the expected
output.
